# Review notes — 1.3.6 / 1.3.7 / 1.4.0 / 1.5.0 / 1.6.0 / 1.6.1 / 1.6.2 / 1.6.3

A pass over the whole app (Kotlin sources, manifest, Gradle files, CI) focused on
bugs, UI smoothness, and making the phone-to-phone Bluetooth gamepad honest.
1.3.6 covers that review; 1.3.7 adds the Linux receiver, whose notes start at
[Linux receiver (1.3.7)](#linux-receiver-137); 1.3.7.2 fixes its face-button
mapping (see [Linux face buttons (1.3.7.2)](#linux-face-buttons-1372)); 1.4.0
takes a latency pass over both halves (see
[Latency pass (1.4.0)](#latency-pass-140)); 1.5.0 adds eight-player support and
per-phone slot selection (see [Player slots (1.5.0)](#player-slots-150)); 1.6.0
adds saved layouts and makes the eight slots the default (see
[Layout presets (1.6.0)](#layout-presets-160) and
[Eight phones by default (1.6.0)](#eight-phones-by-default-160)); 1.6.1 adds a
browser gamepad served by the PC (see
[Browser pad (1.6.1)](#browser-pad-161)); 1.6.2 adds a scannable browser QR in
the console; 1.6.3 fixes asset loading so the page is styled and connects.
This file records what was found and what changed, so the reasoning does not get
lost between releases.

## Fixed

### 1. Three different version numbers

`Brand.VERSION` said **1.3.4**, `build.gradle.kts` said **1.3.5**, and the
README footer said **1.3.3**. The About line in settings is rendered from
`Brand.VERSION`, so users were shown a version that had never been released.

- Both places now say **1.3.6** (`versionCode` 10) and the constant carries a
  comment pointing at `versionName`. The README footer is generated by hand, so
  it now matches too.

### 2. `BluetoothHidGamepad.start()` always claimed success

`start()` returned `true` on API < 28, with Bluetooth switched off, and when
`getProfileProxy` failed. `MainActivity` took that as a green light, flipped
`phoneGamepadActive` on, and started a 60 Hz ticker that sent reports nowhere.
The settings card showed nothing at all, so the only symptom was "it does not
work".

- `start()` now checks the API level, the adapter, and the proxy request and
  returns `false` with a specific status message. `MainActivity` only enables
  the ticker after a real `true`.
- The card gained a live status line: *not running*, *broadcasting, waiting for
  the host*, or *connected*.

### 3. The HID button map did not match the descriptor

The descriptor advertises 16 buttons in the standard gamepad order, but the
report writer copied the wire protocol's PS3 bit order straight into the HID
buttons. Button 1 (A) therefore arrived from **Square**, the D-pad landed in the
shoulder-trigger slots, and the host phone saw scrambled input.

- Added `hidButtons()`, which translates PS3 bits → standard HID bits
  (Cross→1/A, Circle→2/B, Square→3/X, Triangle→4/Y, L1/R1→5/6, L2/R2→7/8,
  Select/Start→9/10, L3/R3→11/12, D-pad→13–16). The wire protocol is unchanged.
- `onGetReport` now answers with a neutral report instead of an empty buffer, so
  a host that polls after connecting cannot latch a stale press.
- The report ID was being passed as `0` but the descriptor has no report IDs;
  the code path is the same, and the descriptor is now documented with the
  report layout in the class comment.
- Removed the `onSetReport` override: acknowledging a report the app does not
  parse told hosts a rumble/LED write had worked.

### 4. The status dot pulsed forever

`GamepadView.setStatus()` set `statusPulse = 1f` on every update. The status
text includes live RTT and battery percentage, so it changes several times a
second — the ripple never finished and the pad invalidated continuously, even
when idle. That is a permanent animation and a steady battery drain.

- The pulse now only starts when the *kind* (idle / linking / connected /
  error) changes.

### 5. Settings sheet re-enumerated every network interface twice a second

`Link.readiness()` and `localSummary()` called `probes(Transport.AUTO)` directly.
Each call walks `NetworkInterface.getNetworkInterfaces()`, and the sheet's ticker
runs every 500 ms on the main thread.

- Added a cached UI probe snapshot with a 1.2 s lifetime (`probesUi()`), refreshed
  on a background thread, invalidated on transport change, `rebind()`, and
  `discover()`. The first call still computes synchronously so the chips are
  correct the instant the sheet opens.

### 6. A second thumb stole a face button

`nearestFace()` picked the closest button even if another pointer already held
it. Landing a second finger on the cluster moved the press away from the first
finger instead of pressing a free button.

- It now skips buttons held by another pointer (`except` keeps the finger's own
  current button eligible while it slides).

### 7. Dead branches in the input path

`releaseNode()` and `publish()` both had `K_FACE -> …` branches identical to the
`else` branch. Removed; behaviour is unchanged, but the intent is no longer
ambiguous (`K_FACE` has no special case).

## Smoother

- **Press animation is a spring.** The old linear interpolation (`pressT +=
  delta * k`) looked mechanical, and its speed depended on the touch-event rate.
  Now a small under-damped spring (`PRESS_STIFFNESS`/`PRESS_DAMPING`) drives
  `pressT`, normalised to 60 Hz frames so 90/120 Hz screens feel the same.
- **Theme cross-fade uses smootherstep** instead of an ease-out cubic, which
  removed the visible kick at the start and end of the fade.
- **Theme picker is a grid of live previews.** Two columns, each tile showing
  the palette's background gradient plus both accent bars. It uses
  `Themes.all.chunked(2)`, so adding a palette needs no picker changes.
- **Touch feedback on buttons and chips** (`pressable()`): a 90 ms 0.955× scale
  down, 180 ms ease back. The listener returns `false`, so clicks still work.
- **HID ticker only sends on change.** It used to push a report every 16 ms
  forever. Now it sends when `PadState.version` changes and polls at 250 ms
  otherwise, and it stops in `onPause()` after sending one neutral report.
- **Settings refresh is one interface scan per tick** instead of one per
  question (readiness, local summary, transport chips).

## Known limits

- Phone-to-phone HID needs **Android 9+** on the controller phone, and the host
  must accept external HID controllers (almost all do).
- The **PS** button is not forwarded over HID; hosts use it for *Home*.
- Bluetooth PAN and USB-to-PC still depend on Android tethering.
- `BluetoothHidDevice` registration depends on the phone's Bluetooth stack; some
  vendor ROMs report *gamepad mode* but never expose the device to other phones.
  The status line now distinguishes "broadcasting" from "connected", so that
  failure is visible instead of silent.

## Linux receiver (1.3.7)

The PC server was Windows-only because ViGEmBus is a Windows kernel driver.
Linux has the same facility in the kernel itself: `uinput` lets an ordinary
program create an input device. The receiver now uses that when it runs on
Linux, and the wire protocol, Android app, and Windows path are untouched.

### Added

- **`pc/linux_pad.py`** — a `LinuxVirtualPad` with the same surface as the
  Windows pad (`ok`, `error`, `rumble_error`, `apply()`, `close()`).
  - Creates a real evdev device through `/dev/uinput`, borrowing the USB ids of
    an **Xbox 360 pad** (`045e:028e`) or a **DualShock 4** (`054c:09cc`, with
    `--pad ds4`) so SDL's controller database, Steam, Proton and RetroArch map
    it automatically.
  - Exposes the xpad layout: face/shoulder/select/start/mode/stick buttons,
    `ABS_X/Y/RX/RY` (−32768…32767), `ABS_Z/RZ` (0…255) and a hat.
  - Writes only changed controls plus one `SYN_REPORT`, so a 140 Hz stream does
    not flood the kernel with redundant events.
  - **Rumble** through `EV_FF`/`FF_RUMBLE`/`FF_GAIN`: effect uploads, play/stop,
    gain scaling, per-effect duration expiry and erase are all handled, then
    converted from Linux's 0…65535 magnitudes to the phone's 0…255.
- **`pc/linux/install-linux.sh`** (and the `install-uinput.sh` alias) +
  **`70-lemogamepad.rules`** — one-shot setup: install the distribution
  packages, load `uinput`, install a udev rule for `/dev/uinput`, add the
  desktop user to the `input` group, create `pc/.venv`, open the firewall and
  add a launcher.
- **`pc/build_linux.sh`** — single-file PyInstaller build (`dist/lemoGamePad-server`).
- **`pc/test_linux_pad.py`** — verifies the created device, capabilities, button
  and axis events, and the full rumble path (uploaded and played from a child
  process, like a real game).
- `requirements.txt` now selects `evdev` on Linux and `vgamepad` on Windows.

### Fixed while adding it

- **Force-feedback requests are not where they look.** Recent kernels queue
  `EV_UINPUT` upload/erase requests on the **uinput fd**, while `EV_FF`
  play/stop and `FF_GAIN` arrive on the created event node. The backend watches
  both and parses raw `input_event` records from the uinput fd.
- **python-evdev 2.0.0's `begin_upload()`/`begin_erase()` are broken**: they
  assign a stray `effect_id` attribute instead of `request_id`, so every ioctl
  targets request 0 and only the first effect works. The backend performs the
  ioctl itself with the correct request id.
- **Token 0 is no longer accepted for input** (it means "assign me", so several
  phones could otherwise collide on one peer), and discovery never hands out 0
  or an already-connected token.
- **Ports are validated** (`1…65535`), including the derived `port + 1` video
  port, so the banner and QR can no longer advertise port 0 or 65536.
- **Capture failures are reported instead of dying silently** — headless,
  Wayland-without-XWayland and RDP sessions now print why the screen preview is
  unavailable, and repeated failures are logged once.
- **Slow video viewers survive a hiccup**: a send timeout drops one frame
  instead of disconnecting the phone (the timeout also rose from 0.75 s to 5 s).
- **Quality acknowledgement echoes the profile actually used**, not an unknown
  request byte.
- **Server defaults now match the CLI** (20 fps / 800 px / quality 50), so
  direct construction and `--video-*` agree.

### Linux notes

- No root at runtime; `/dev/uinput` write access is the only requirement.
- The server never runs `sudo`, pip-installs, or edits firewall rules on Linux;
  it prints the exact commands instead (PEP 668 makes silent installs unsafe).
- `test_rumble.py` is Windows/XInput-only and now exits cleanly elsewhere; use
  `test_linux_pad.py` on Linux.


## Linux face buttons (1.3.7.2)

The 1.3.7 Linux receiver swapped square/triangle (SDL X/Y) for every pad
identity. The face-button map now depends on the identity being emulated:

- **Xbox 360 (`x360`, default)** — square is `BTN_X`, triangle is `BTN_Y`.
- **DualShock 4 (`--pad ds4`)** — square is `BTN_WEST`, triangle is `BTN_NORTH`.

The reason is that `BTN_X`/`BTN_Y` are aliases of `BTN_NORTH`/`BTN_WEST`, and
SDL/Steam pick their mapping from the virtual pad's USB vendor and product IDs.
Matching the codes to the identity keeps X on the left and Y on top in both
cases. `pc/test_linux_pad.py` exercises both identities.


## Latency pass (1.4.0)

The complaint was not "latency is high" but "latency is fine and then it spikes".
That shape has a specific set of causes, and most of them were on the receiving
side rather than the network itself. This pass removes the avoidable queues and
makes the remaining variation visible.

### What was actually causing the spikes

1. **The PC applied every queued datagram, one at a time.** `recvfrom` was
   followed by a full pad update for each packet. When the phone sent a burst
   (a stick flick, or a wake-up after the radio dozed), the kernel queue was
   drained oldest-first, so the virtual pad replayed several *old* positions
   before reaching the current one. Games sampled those intermediate frames and
   showed the stick dragging behind the thumb.
2. **A late datagram could rewind the pad.** UDP does not preserve order. One
   packet overtaking another snapped the sticks back for a frame — visually a
   twitch, and exactly the "it stutters sometimes" report.
3. **The receive thread also rendered the console status line.** On Windows,
   selecting text in the console (QuickEdit) blocks `WriteConsole` until the
   user presses a key. The whole input path froze for as long as the selection
   was held. This one produced multi-second stalls that looked like network
   failure.
4. **The phone polled its own state every 7 ms.** Input latency depended on the
   poll timer plus whatever the scheduler did with the sender thread, not on the
   network. A busy UI thread could delay a sample by a frame or more.
5. **Wi-Fi power save.** Between packets Android parks the radio. On an idle
   link that is invisible; during play the first packet after a quiet moment
   pays 50-300 ms. This is the single most common cause of "sometimes it lags"
   on an otherwise healthy Wi-Fi link.
6. **Small socket buffers.** A short scheduling stall on either side dropped
   datagrams that a larger buffer would have absorbed.

### Fixed

- **Bursts collapse to the newest state.** The receiver now drains the socket
  with `select` + non-blocking `recvfrom` (up to `MAX_DRAIN` packets per pass),
  keeps only the newest state per phone, and applies it once. Ten queued stick
  samples become one update at the current position. `pc/test_latency.py` sends
  30 packets and asserts exactly one pad update.
- **Out-of-order packets are discarded.** Each peer tracks the last applied
  16-bit sequence number; `_seq_newer()` handles wrap-around. A packet older
  than the last applied one is dropped instead of rewinding the sticks. The
  counter is reset when the phone changes address (a new socket starts its
  sequence at 1) or after a 2 s gap, so a reconnect is never mistaken for a
  stale packet.
- **The console can no longer stall input.** Status printing moved to its own
  thread which reads a snapshot; the receive loop never calls `print`. The
  status line gained a `N lost` counter.
- **Larger UDP buffers.** `SO_RCVBUF`/`SO_SNDBUF` are raised to 512 KB on the
  PC (best effort — the OS may clamp it).
- **Higher thread priority on both ends.** The PC receive thread asks for
  elevated priority (and a 1 ms timer resolution on Windows); the phone's sender
  and receiver run at `THREAD_PRIORITY_DISPLAY`.
- **Event-driven phone sender.** `PadState.bump()` now invokes an `onChange`
  callback, which `LockSupport.unpark()`s the sender. Standard mode sends the
  frame immediately on change instead of waiting for the next 7 ms tick;
  keepalives still run twice a second so the PC never releases a held button.
- **Wi-Fi low-latency lock.** While connected over Wi-Fi the app holds a
  `WIFI_MODE_FULL_LOW_LATENCY` lock (falling back to the high-performance lock
  below API 29) and releases it on stop/disconnect. Requires the new
  `WAKE_LOCK` permission; it is not held on USB/Bluetooth tethering.
- **Low-delay marking.** Sockets set `IPTOS_LOWDELAY` and 64 KB buffers. Every
  hint is wrapped so a ROM that rejects one cannot kill the link.

### Added

- **RTT history with average, min, max and jitter.** Each PONG updates the
  numbers now shown next to the connection status, and the last 60 samples
  (~30 s) are stored for the settings sparkline.
- **Latency sparkline in settings.** A small graph under the status card plots
  the history and labels the peak. A flat line at 12 ms and a sawtooth to 250 ms
  look completely different, which is the point.
- **Uplink loss figure.** The PC counts sequence gaps per phone and appends the
  loss (permille) to the PONG trailer. Old apps ignore the extra bytes; the new
  app shows `% loss` in the status pill and settings stats. `-1` means "no data".
- **Input rate modes.** `ECO` (only on change, 900 ms keepalive), `STANDARD`
  (event-driven, recommended) and `TURBO` (250 Hz continuous) in settings.
- **Stick precision curve.** A 0-100% shaping slider: 0 is linear, higher values
  keep small corrections near the centre while preserving full deflection.
  Applied in `GamepadView.axes()`.
- **Vibration strength.** A 0-100% multiplier on incoming rumble, so a phone
  with an aggressive motor can be tamed without disabling haptics.

### Protocol compatibility

The wire format is unchanged. PONG still carries the 4-byte clock echo; 1.4
servers add an optional 2-byte loss field in the trailer, and 1.4 apps treat
its absence as "unknown". Input packets, headers, PS3 bit order and discovery
are byte-for-byte identical, so a 1.4 phone works with a 1.3 server and vice
versa.

### Tests

- `pc/test_latency.py` — burst coalescing, out-of-order discard, 16-bit
  wrap-around, new-socket sequence restart, PONG loss trailer, clean shutdown.
- `pc/test_multi.py` — unchanged, still passes (slot limit, routing, idle
  release, reconnect).
- Compile check: `python3 -m py_compile pc/*.py`.

## Player slots (1.5.0)

### Why

With more than four phones, connection order decided the player number. A phone
that joined late could not become player 2 without reconnecting everyone, and
phones that moved between Wi-Fi/USB could shuffle the order. The settings sheet
now lets each phone ask for a pad directly.

### Design

- **One extra byte on INPUT.** `want_pad` follows the existing pad-type byte:
  `0` keeps the old automatic behaviour, `1`…`8` requests P1…P8. It is optional,
  so 1.5 phones work with 1.4 servers and 1.5 servers still accept 1.4 phones.
- **Prefer, do not steal.** At registration a free requested pad is used.
  A busy pad falls back to the next free one; the request is retried on later
  packets, so the phone moves as soon as that pad frees up. Another phone's live
  pad is never taken.
- **Live moves.** An already-connected phone can change its request from the
  settings sheet. The server neutralises and releases the old pad, assigns the
  new one, and logs the move. The sequence/position state is preserved, so the
  first packet on the new pad is not treated as a duplicate.
- **Assignment feedback.** PONG appends the assigned pad after the loss field.
  The app shows it in the status pill and next to the P1–P8 selector, including
  the “P3 is busy — using P5” case.
- **Cap.** `MAX_PHONES` is 8 and the CLI/storage clamp uses it. XInput still
  exposes four pads on Windows; slots 5–8 are for `--pad ds4`, DirectInput/Raw
  Input and Linux.

### Tests

- `pc/test_multi.py` — requested P3 lands on slot 3, PONG reports it, a second
  request falls back, a connected phone moves live, and an occupied pad is not
  stolen.
- Android `:app:assembleDebug` still builds; the selector is persisted in
  `PrefsKeys.PLAYER_SLOT` and sent immediately when changed.

## Layout presets (1.6.0)

### Why

The pad has always had one custom arrangement. Players who use the phone in
different positions (on a desk, in a grip, on a tablet stand) had to redraw all
controls by hand each time, and there was no way to keep a known-good layout
before experimenting.

### Design

- **Live layout stays where it was.** `PrefsKeys.LAYOUT` is still the active
  snapshot, so updating from an older version keeps the arrangement the user
  already had. The preset list lives beside it in `PrefsKeys.LAYOUTS`, with the
  active name in `PrefsKeys.LAYOUT_ACTIVE`.
- **Named copies, not modes.** A preset stores the same `layoutSnapshot()` string
  (positions, scale and hidden flags) that the editor already writes. Switching
  simply applies that string, so no second layout format can drift from the
  editor.
- **Editing follows the active preset.** `persistLayout()` writes the live
  snapshot and, when a preset name is active, updates that preset in place.
  "Save as" is the explicit way to fork a copy; "Default" clears the name and
  resets the pad.
- **Safe storage.** The list is a JSON array in one preference, so names may
  contain punctuation and order is stable. A corrupt list is ignored rather
  than crashing the sheet, and a stale active name is cleared on startup.
- **Themed dialogs.** Saving and deleting use lightweight views added to the
  activity's decor view instead of platform dialogs, so they match the selected
  palette and sit above the immersive pad. They close on Back, on the scrim, or
  when the activity pauses/destroys.

### Tests

- Android `:app:assembleDebug` builds after adding the store, dialogs and card.
- Manual checks expected: save two layouts, switch between them, edit the active
  one and switch away/back, delete the active one, and restart the app.

## Eight phones by default (1.6.0)

### Why

1.5.0 could hold eight phones, but `--max-phones` still defaulted to four. A
fifth phone was therefore rejected unless the user knew to pass the flag, which
looks exactly like "eight-player support does not work".

There is also a separate Windows limit that cannot be coded away: XInput, the
API most PC games use, exposes only four controllers. Creating eight XInput
devices is possible in ViGEm, but the game can never open more than four.

### Design

- **Default 8.** The constructor and the command line now default to eight
  slots. Pads are still created lazily, so unused slots cost nothing.
- **Mixed backends on Windows.** With the default `--pad x360`, slots 1–4 stay
  Xbox 360/XInput and slots 5–8 automatically use the DualShock 4/HID backend.
  The extra pads are visible to DirectInput, Raw Input, emulators and tools
  such as Steam, even though XInput-only titles still stop at four. `--pad ds4`
  still makes all eight DirectInput devices; Linux keeps eight Xbox 360 evdev
  pads.
- **Honest banner.** When the mix is active the header names both backends and
  prints `Pads 5-8 : DS4/DirectInput (XInput only allows four pads)`, so the
  four-pad result in an XInput game is explained rather than silent.

### Tests

- `pc/test_multi.py` asserts the default is eight, the cap is still eight, the
  Windows mix is exactly four `x360` + four `ds4`, and Linux keeps eight `x360`
  slots.
- The existing multi-phone, slot-selection, rumble, idle and reconnect tests
  still pass.

## Browser pad (1.6.1)

The remaining gap was the device itself: an iPhone, a laptop or a phone without
the APK could not join. WebRTC and a hosted page would add dependencies and an
internet requirement, so the page is served by the same Python process.

### Design

- **Stdlib only.** `pc/web_ui.py` implements the HTTP server and WebSocket
  framing directly. The page is plain HTML/CSS/JS in `pc/web/`; there is no
  framework, bundler, CDN or new Python package.
- **One input path.** Browser messages are converted to `InputState` and sent
  through `_submit_input`, the same function UDP packets use. Slots,
  coalescing, sequence handling, idle release and the eight-pad limit therefore
  cannot drift between transports.
- **Pairing key.** Every run generates `secrets.token_urlsafe(6)` unless
  `--web-key` pins one. The page and all assets require `?k=`, and WebSocket
  upgrades additionally require a same-host `Origin`. CSP blocks remote loads.
- **Rumble routing.** A `Peer.web_send` callback sends motor speeds down the
  tab's WebSocket instead of to a UDP address. Phones keep the existing path.
- **Packaging.** Both PyInstaller builds pass `--add-data` for `pc/web`, so the
  single-file EXE and Linux binary still serve the page.

### Tests

- `pc/test_web.py` drives a real server over loopback: page and asset auth,
  wrong key (`401`), cross-site origin (`403`), input and clamping, requested
  P2, ping/RTT response, rumble delivery and disconnect release. CI runs it.
- All existing PC suites still pass.
- 1.6.2 prints the browser URL as a console QR through the same helper the
  phone pairing QR uses; the saved web PNGs still cover every LAN address.
- 1.6.3 fixes a real-browser-only bug: requiring the key on every asset made
  `style.css` and `app.js` return `401`, because a browser requests them
  without the page's query string. Assets are public code and now load without
  the key; the page and WebSocket still require it. `test_web.py` fetches the
  assets exactly as a browser does.
